# Phase 1 - 基础可运行 MVP 阶段

## 1. 阶段目标

完成项目最核心的业务闭环，交付一个可运行的前后端分离单体系统。

用户在本阶段应能够完成：

- 注册和登录。
- 上传简历文件。
- 查看简历文本提取结果。
- 查看基础结构化解析结果。
- 获取 AI 简历分析结果。
- 选择目标岗位并查看匹配结果。
- 查看针对目标岗位的基础优化建议。

本阶段重点不是功能复杂度，而是打通“登录 -> 上传简历 -> 解析简历 -> AI 分析 -> 岗位匹配 -> 优化建议展示”的主流程。

说明：
- 本阶段优先保证主流程闭环清晰、可演示、可讲解。
- 历史记录作为 Phase 1 收尾能力实现，优先采用聚合查询方式，不单独设计复杂行为流水。
- 岗位数据以“系统预置或开发期导入”为主，不要求本阶段必须完成完整后台管理页面。

---

## 2. 阶段定位

Phase 1 是项目第一版，也是后续所有阶段的基础版本。

本阶段产出必须满足以下要求：

- 可以本地启动并完整演示。
- 业务主流程闭环清晰。
- 技术选型不过度复杂，优先保证可实现、可维护、可讲解。
- 设计上为 Phase 2 工程化增强和 Phase 3 AI 深化预留扩展空间。

## 4. MVP 功能范围

### 4.1 本阶段核心必须完成

- 用户注册
- 用户登录
- JWT 鉴权
- 简历上传
- 简历文件存储
- 简历文本提取
- 简历结构化解析基础版
- AI 简历分析基础版
- 基于预置岗位的单岗位匹配
- 针对目标岗位的基础优化建议展示

### 4.2 本阶段尽量完成但不是主链路阻塞项

- 基础历史记录页面
- 岗位列表展示
- 岗位详情展示

### 4.3 本阶段不做

- 复杂管理后台
- 细粒度权限体系
- 岗位管理后台页面
- 向量语义匹配
- RAG 检索增强
- 多轮对话
- 微服务拆分
- 消息队列
- 复杂数据统计
- 生产级高可用部署
- 复杂文件去重策略
- 复杂行为审计系统

说明：
本阶段如果需要维护岗位数据，可通过 SQL 初始化脚本、JSON 导入或开发期接口完成，不要求建设正式后台管理页面。

## 5. 总体排期

建议排期为 6 个迭代。每个迭代形成一个可验证版本，最后一个迭代用于联调、修复和演示材料整理。

| 迭代 | 主题 | 核心产出 |
| --- | --- | --- |
| v0.1 | 项目基线与用户认证 | 前后端项目可启动，注册登录和 JWT 鉴权可用 |
| v0.2 | 简历上传与文件存储 | 用户可以上传简历，文件和元数据可以保存 |
| v0.3 | 文本提取与结构化解析 | 系统可以提取简历文本并生成基础结构化结果 |
| v0.4 | AI 简历分析 | 系统可以基于简历内容生成基础分析结果 |
| v0.5 | 岗位匹配与优化建议 | 系统可以基于预置岗位输出匹配结果和优化建议 |
| v0.6 | 历史记录、联调与演示 | 主流程完整可演示，基础历史记录可查看 |

说明：
- 若个人时间有限，可以将“每周”理解为一个开发迭代，不强制绑定自然周。
- 若 v0.5 压力较大，岗位列表与详情页可简化，但匹配与建议主流程必须完成。

## 6. 任务拆解与验收标准

### v0.1 - 项目基线与用户认证

#### 目标

建立前后端项目基础结构，完成用户注册、登录和 JWT 鉴权。

#### 任务拆解

- 后端确认 Java、Spring Boot、数据库和依赖版本。
- 创建 Spring Boot 应用入口。
- 配置 PostgreSQL 数据源。
- 设计用户表。
- 实现用户注册接口。
- 实现用户登录接口。
- 生成和校验 JWT。
- 配置 Spring Security 鉴权规则。
- 前端创建 Vue 3 项目结构。
- 实现登录页和注册页。
- 前端保存 Token，并在请求中携带 Token。
- 增加基础路由守卫。

#### 建议 API

- `POST /api/auth/register`
- `POST /api/auth/login`
- `GET /api/users/me`

#### 验收标准

- 后端应用可以正常启动。
- 前端应用可以正常启动。
- 用户可以通过前端完成注册。
- 用户可以通过前端完成登录。
- 登录成功后前端可以拿到 JWT。
- 未登录用户访问受保护接口时被拒绝。
- 已登录用户可以访问 `GET /api/users/me`。
- 密码不能明文存储。
- 本轮结果记录到 `docs/iteration-log/v0.1-auth.md`。

---

### v0.2 - 简历上传与文件存储

#### 目标

完成简历上传闭环，保存简历文件和简历元数据。

#### 任务拆解

- 设计简历元数据表。
- 定义支持的文件类型和大小限制。
- 集成 MinIO 或本地兼容存储实现。
- 实现文件存储服务。
- 实现简历上传接口。
- 保存文件路径、原始文件名、文件类型、文件大小、上传用户和上传时间。
- 实现简历列表接口。
- 实现简历详情接口。
- 前端实现简历页面中的上传区域。
- 前端实现简历列表展示。

#### 上传策略

- Phase 1 允许重复上传，不做文件内容去重。
- 支持 PDF、DOC、DOCX。
- 不支持的文件类型直接拒绝。
- 文件大小限制在配置中统一管理。

#### 建议 API

- `POST /api/resumes`
- `GET /api/resumes`
- `GET /api/resumes/{id}`

#### 验收标准

- 已登录用户可以上传 PDF 或 Word 简历。
- 未登录用户不能上传简历。
- 超过大小限制的文件会被拒绝。
- 不支持的文件类型会被拒绝。
- 上传成功后文件可以在存储服务中找到。
- 上传成功后数据库中有对应元数据。
- 用户只能查看自己的简历记录。
- 前端可以展示上传后的简历列表。
- 本轮结果记录到 `docs/iteration-log/v0.2-upload.md`。

---

### v0.3 - 文本提取与结构化解析

#### 目标

从已上传简历中提取文本，并生成基础结构化解析结果。

#### 任务拆解

- 集成 Apache PDFBox 处理 PDF。
- 集成 Apache POI 处理 Word。
- 实现简历文本提取服务。
- 设计解析结果表。
- 定义基础结构化字段。
- 实现基础规则解析。
- 实现解析触发接口。
- 实现解析结果查询接口。
- 前端展示文本提取结果。
- 前端展示结构化解析结果。

#### 基础结构化字段

- 姓名
- 手机号
- 邮箱
- 教育经历
- 项目经历
- 实习或工作经历
- 技能关键词
- 原始文本

#### 解析策略

- Phase 1 只要求基础解析可用，不追求复杂版式高精度识别。
- 图片型简历、扫描型简历、复杂表格布局简历不作为本阶段重点支持对象。
- 重复解析同一份简历时，默认覆盖旧解析结果，保留最新一次结果。

#### 建议 API

- `POST /api/resumes/{id}/parse`
- `GET /api/resumes/{id}/parse-result`

#### 验收标准

- 系统可以从 PDF 简历中提取文本。
- 系统可以从 Word 简历中提取文本。
- 解析失败时返回明确错误信息。
- 解析结果可以保存到数据库。
- 重复解析同一份简历时结果处理策略明确。
- 前端可以查看原始文本和结构化结果。
- 解析器当前限制已记录在迭代日志中。
- 本轮结果记录到 `docs/iteration-log/v0.3-parse.md`。

### v0.4 - AI 简历分析

#### 目标

基于解析后的简历内容，生成基础 AI 分析结果。

#### 任务拆解

- 接入 Spring AI。
- 配置 AI 服务 Key 和模型参数。
- 设计 AI 分析结果表。
- 设计第一版提示词模板。
- 定义 AI 输出 JSON 结构。
- 实现简历分析服务。
- 实现 AI 分析触发接口。
- 实现 AI 分析结果查询接口。
- 前端展示 AI 分析结果。
- 记录 AI 调用失败和超时场景。

#### 分析维度

- 简历完整度
- 技能表达
- 项目经历表达
- 实习或工作经历表达
- 问题清单
- 优化建议摘要

#### AI 输出要求

AI 输出必须转换为系统约定的结构化结果，前端不得直接依赖自由文本渲染关键字段。

建议最少包含以下结构：

- 完整度评分
- 优势列表
- 问题列表
- 建议摘要
- 模型名称
- 提示词版本
- 分析时间

#### 建议 API

- `POST /api/resumes/{id}/ai-analysis`
- `GET /api/resumes/{id}/ai-analysis`

#### 验收标准

- 已解析简历可以触发 AI 分析。
- 未解析简历不能直接触发 AI 分析，或系统会提示先解析。
- AI 分析结果可以保存到数据库。
- 前端可以展示分析结果。
- AI 调用失败时不会导致系统崩溃。
- AI 输出不能编造用户不存在的经历。
- AI 输出必须落为受控结构。
- AI 返回格式错误时不得保存脏数据。
- 提示词版本记录在代码或数据库中。
- 本轮结果记录到 `docs/iteration-log/v0.4-ai-analysis.md`。

### v0.5 - 岗位匹配与优化建议

#### 目标

基于预置岗位数据，完成简历与岗位的基础匹配，并输出优化建议。

#### 任务拆解

- 设计岗位表。
- 通过 SQL、JSON 导入或开发期接口预置岗位数据。
- 实现岗位列表接口。
- 实现岗位详情接口。
- 设计岗位匹配结果表。
- 实现基础关键词匹配算法。
- 实现岗位匹配接口。
- 生成匹配分数和匹配说明。
- 基于匹配差距生成优化建议。
- 前端实现岗位列表。
- 前端实现岗位详情。
- 前端展示岗位匹配结果和优化建议。

#### 说明

- 本阶段不要求实现完整岗位管理后台页面。
- 岗位数据以“可用”为原则，优先保证匹配主流程成立。
- Phase 1 匹配范围以“单份简历 + 单个岗位”为主。

#### 建议 API

- `GET /api/jobs`
- `GET /api/jobs/{id}`
- `POST /api/resumes/{resumeId}/job-matches`
- `GET /api/resumes/{resumeId}/job-matches`
