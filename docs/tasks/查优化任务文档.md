# AI 简历优化与岗位匹配系统：Codex 逐步检查优化任务文档

## 1. 项目主线与边界冻结

### 1.1 当前推荐主流程

```text
注册 / 登录
↓
工作台
↓
上传简历
↓
简历解析
↓
简历诊断
↓
新增或选择目标岗位
（优先粘贴真实招聘 JD，也可选择系统样例岗位）
↓
目标岗位解析
↓
匹配分析
↓
岗位优化建议
↓
局部改写
↓
采纳 / 拒绝改写建议
↓
AI 结果回看
```

### 1.2 当前不建议继续扩展的内容

| 功能 | 当前处理方式 | 原因 |
|---|---|---|
| 管理员岗位管理 | 暂不做 | 普通用户侧已有岗位库，不要混入后台语义 |
| 岗位爬虫 / 外部岗位自动采集 | 暂不做 | 会引入反爬、登录、版权、合规、数据过期和清洗复杂度，不符合当前实习项目重点 |
| 完整简历自动生成 | 暂不做 | 容易编造经历，也会扩大 AI 责任边界 |
| 简历 DOCX / PDF 导出 | 暂不做 | 当前重点是匹配与建议闭环 |
| 复杂 Dashboard | 暂不做 | 容易变成展示堆叠，优先稳定主流程 |
| 微服务化 | 不做 | 个人实习项目不需要，反而增加复杂度 |
| 大规模数据库重构 | 暂不做 | 当前先修边界和命名，不打断开发节奏 |

### 1.3 目标岗位输入方案与岗位来源边界

当前主流程应优先支持用户手动粘贴目标岗位 JD，而不是爬取岗位信息。

推荐产品定位：

```text
用户在招聘网站、公司官网、牛客、Boss、实习僧等平台看到岗位
↓
复制岗位描述 JD
↓
粘贴到本系统的“新增目标岗位”页面
↓
系统解析岗位要求
↓
选择自己的简历进行匹配分析
↓
生成岗位优化建议和局部改写
```

#### 1.3.1 岗位来源类型

建议统一使用 `sourceType` 区分岗位来源：

| sourceType | 含义 | 用途 | 是否主流程 |
|---|---|---|---|
| `USER_INPUT` | 用户粘贴的真实目标岗位 JD | 真实求职匹配与优化 | 是 |
| `PRESET` | 系统预置岗位样例 | 演示、测试、参考 | 否，可作为辅助入口 |
| `CRAWLED` | 外部爬取岗位 | 当前不实现 | 否 |

#### 1.3.2 目标岗位与岗位库的区别

| 功能 | 面向对象 | 数据来源 | 作用 | 不做什么 |
|---|---|---|---|---|
| 目标岗位 | 当前用户 | 用户粘贴 JD | 用于真实匹配、建议和改写 | 不展示全站岗位，不做系统岗位维护 |
| 岗位库 | 普通用户 | 系统预置样例 | 用于参考和演示 | 不作为用户真实投递目标，不承担管理后台职责 |
| 岗位管理 | 管理员，当前未实现 | 后台维护 | 维护系统岗位库 | 普通用户不可见 |

#### 1.3.3 推荐数据模型方向

如果项目已有 `job_descriptions` 或类似表，优先复用，不强制大改表结构。建议至少具备以下语义字段：

```text
id
user_id
title
company_name
source_type
raw_description
parsed_result_json
created_at
updated_at
```

其中：

- `raw_description`：保存用户粘贴的岗位 JD 原文。
- `parsed_result_json`：保存岗位解析结构，例如岗位名称、职责、必备技能、加分技能、关键词、经验要求。
- `source_type`：区分 `USER_INPUT` 和 `PRESET`。

#### 1.3.4 推荐接口边界

```text
POST /api/job-descriptions
创建目标岗位，保存用户粘贴的 JD

POST /api/job-descriptions/{id}/parse
解析目标岗位 JD

GET /api/job-descriptions
查询当前用户的目标岗位历史

GET /api/job-descriptions/{id}
查看目标岗位详情

POST /api/resumes/{resumeId}/job-matches
基于简历和目标岗位生成匹配分析
```

匹配接口推荐请求体：

```json
{
  "jobDescriptionId": 1
}
```

不建议当前阶段新增爬虫接口，例如：

```text
POST /api/jobs/crawl
POST /api/external-jobs/import
```

#### 1.3.5 验收标准

- 新增目标岗位页面支持粘贴完整 JD 原文。
- 目标岗位解析只解析 JD，不判断简历匹配度。
- 匹配分析必须基于“已解析简历 + 目标岗位”。
- 岗位库只作为系统样例或参考，不替代目标岗位。
- 普通用户侧不出现“岗位管理”语义。
- 项目中不存在必须依赖爬虫才能完成主流程的逻辑。

## 4. 阶段 2：检查并收紧后端 Controller / Service 职责

### 4.1 任务目标

保证 Controller、Service、AI 调用、Prompt、结果解析之间职责清晰。该阶段优先轻量拆分，不做大规模重构。

### 4.2 推荐职责边界

| 层级 | 应该做什么 | 不应该做什么 |
|---|---|---|
| Controller | 接收参数、获取当前用户、调用 Service、返回 Result/VO | 不写复杂业务逻辑，不拼 Prompt，不直接操作数据库 |
| Service | 业务编排、权限校验、状态流转、调用 Mapper / AI 组件 | 不堆所有功能，不直接写超长 Prompt |
| Mapper / Repository | 数据库 CRUD | 不写业务判断，不调用 AI |
| AI Client | 统一调用大模型 | 不理解具体业务含义 |
| Prompt Template | 管理 Prompt 文本和版本 | 不访问数据库 |
| Result Parser | 解析 AI 返回 JSON / 文本 | 不做业务流程编排 |

### 4.3 推荐服务拆分方向

如果当前存在大 Service，可以按以下方向逐步拆：

```text
ResumeService：简历记录、列表、删除、权限校验
ResumeParseService：简历文本提取和结构化解析
ResumeDiagnosisService：简历诊断 AI 逻辑
TargetJobService：目标岗位新增、列表、详情、删除
TargetJobParseService：目标岗位解析 AI 逻辑
MatchAnalysisService：简历与目标岗位匹配分析
JobSuggestionService：岗位优化建议
RewriteSuggestionService：局部改写和采纳状态
JobOptimizationReportService：聚合已有结果生成报告视图
AiHistoryService：AI 结果回看
AiClient / AiChatClient：统一模型调用
PromptTemplateService：统一 Prompt 管理
```

注意：如果当前类名不同，不强行改名；先按职责拆方法和组件。

### 4.4 需要重点防止的错误

| 错误 | 正确做法 |
|---|---|
| Controller 里拼 Prompt | 移到 Prompt 模板类或资源文件 |
| Service 一个方法完成匹配、建议、改写、报告 | 拆成多个 Service，由页面或应用服务按需调用 |
| 报告接口重新调用 AI | 报告只查询并聚合已有结果 |
| 局部改写自动写回简历文件 | 只保存改写建议和采纳状态 |
| 简历诊断输出岗位匹配建议 | 简历诊断只看简历本身 |
| 目标岗位解析输出简历建议 | 目标岗位解析只解析 JD |
| 用户粘贴 JD 被写入系统岗位库 | 用户粘贴内容保存为目标岗位，sourceType=USER_INPUT |
| 岗位库和目标岗位共用同一页面语义 | 岗位库只读参考，目标岗位用于匹配主流程 |
| 为主流程新增爬虫依赖 | 当前不做爬虫，主流程依赖用户粘贴 JD |

### 4.5 验收标准

- Controller 中没有大段业务逻辑。
- Prompt 不直接散落在多个 Controller 中。
- 报告接口没有重新调用 AI。
- 局部改写不会自动修改原始简历。
- 用户粘贴目标岗位不会被当成系统预置岗位管理数据。
- 后端不存在必须依赖爬虫才能完成匹配主流程的逻辑。
- 后端测试或编译通过。

建议验证命令：

```bash
# 或
mvn test
```

如果当前测试不完整，至少执行：


## 5. 阶段 3：统一 AI Prompt 管理

### 5.1 任务目标

把散落在代码里的 Prompt 收拢到统一位置，降低后续维护成本。

### 5.2 推荐目录

二选一即可：

方案 A：Java 类管理

```text
backend/src/main/java/.../ai/prompt
├── ResumeDiagnosisPrompt.java
├── TargetJobParsePrompt.java
├── MatchAnalysisPrompt.java
├── JobSuggestionPrompt.java
└── RewriteSuggestionPrompt.java
```

方案 B：资源文件管理

```text
backend/src/main/resources/prompts
├── resume-diagnosis-v1.md
├── target-job-parse-v1.md
├── match-analysis-v1.md
├── job-suggestion-v1.md
└── rewrite-suggestion-v1.md
```

个人项目推荐优先使用方案 B，便于阅读和修改。

### 5.3 每个 Prompt 必须标记的信息

| 字段 | 说明 |
|---|---|
| promptName | Prompt 名称 |
| promptVersion | 版本，例如 v1 |
| input | 输入字段 |
| output | 输出格式 |
| constraints | 约束，例如不编造经历、不自动改写原简历 |

### 5.4 AI 输出格式要求

优先要求模型输出 JSON，至少保证每类结果结构稳定。

示例：岗位优化建议输出结构

```json
{
  "summary": "总体建议摘要",
  "suggestions": [
    {
      "type": "SKILL_GAP",
      "priority": "HIGH",
      "problem": "当前问题",
      "suggestion": "建议做法",
      "evidence": "依据",
      "warning": "注意事项"
    }
  ]
}
```

### 5.5 验收标准

- 每类 AI 功能都能找到独立 Prompt。
- Service 中不再出现超长 Prompt 字符串。
- Prompt 有版本号。
- AI 结果表或 VO 中尽量保留 `modelName`、`promptVersion`。
- 后端编译通过。

## 6. 阶段 4：明确报告接口只做聚合

### 6.1 任务目标

检查岗位优化报告相关接口和 Service，确保报告不是新的 AI 生成功能。

### 6.2 报告应该聚合的数据

| 数据 | 来源 |
|---|---|
| 简历基本信息 | resume 记录 |
| 简历解析结果 | resume parse result |
| 目标岗位信息 | 用户粘贴的 job description / target job，或系统样例岗位 |
| 目标岗位解析结果 | target job parse result |
| 匹配分和匹配依据 | AI 匹配结果 |
| 岗位优化建议 | AI suggestion 结果 |
| 局部改写建议 | rewrite suggestion 结果 |
| 采纳 / 拒绝状态 | rewrite accept status |
| warning / 下一步清单 | 可由已有建议整理，不重新请求 AI |

### 6.3 报告不应该做的事

- 不重新调用 AI。
- 不重新生成匹配结论。
- 不重新生成优化建议。
- 不生成完整定制简历。
- 不导出 DOCX / PDF。
- 不编造用户经历、项目、技能或量化数据。

### 6.4 推荐报告 VO

```java
public class JobOptimizationReportVO {
    private Long resumeId;
    private String resumeName;
    private Long jobDescriptionId;
    private String jobTitle;
    private MatchSummaryVO matchSummary;
    private List<JobSuggestionVO> suggestions;
    private List<RewriteSuggestionVO> rewriteSuggestions;
    private List<String> warnings;
    private List<String> nextSteps;
    private String modelName;
    private String promptVersion;
}
```

字段名称以项目现有规范为准，不要求完全照抄。

### 6.5 验收标准

- 报告 Service 中没有 AI Client 调用。
- 报告接口只查询已有结果。
- 如果某类结果不存在，报告能给出空状态或提示，而不是报错。
- 前端能清楚展示报告只是汇总结果。

## 8. 阶段 6：DTO / VO / Entity 边界检查

### 8.1 任务目标

检查后端是否存在 Entity 直接返回给前端、DTO 和 VO 混用、接口字段职责不清的问题。

### 8.2 边界规则

| 类型 | 职责 |
|---|---|
| Entity | 数据库表映射，只在后端内部使用 |
| RequestDTO | 接收前端请求参数 |
| ResponseVO | 返回给前端展示 |
| Command / Query | 可选，用于 Service 内部表达业务动作 |

### 8.3 重点检查

- Controller 是否直接返回 Entity。
- VO 是否包含前端不需要的数据库字段。
- DTO 是否被 Mapper 当作 Entity 使用。
- AI 返回原文是否直接暴露给前端，是否需要结构化处理。
- 是否存在一个 VO 同时承担匹配、建议、改写、报告四种展示。

### 8.4 验收标准

- 关键接口返回 VO，不直接返回 Entity。
- 请求参数使用 DTO。
- AI 相关结果 VO 按功能拆分。
- 后端编译通过。

## 12. 进入第四阶段前的架构优化启动清单

该清单用于在正式开启第四阶段“架构演进”前，确认当前功能边界已经收敛，避免把产品边界问题带入架构重构。

### 12.1 必须先确认的问题

| 检查项 | 目标状态 |
|---|---|
| 简历解析 | 允许继续优化质量，但不阻塞架构边界审查 |
| 目标岗位输入 | 用户粘贴 JD 是主流程，系统预置岗位只是辅助样例 |
| 简历诊断 | 只分析简历本身，不绑定岗位 |
| 目标岗位解析 | 只解析 JD，不输出简历建议 |
| 匹配分析 | 只回答简历与目标岗位是否匹配 |
| 岗位优化建议 | 输出行动建议，不直接改写原文 |
| 局部改写 | 只改写用户选中的片段，不自动写回原简历 |
| 岗位优化报告 | 聚合已有结果，不重新调用 AI |
| AI 历史 | 只做回看，不触发新生成 |

### 12.2 第四阶段前建议先做的轻量动作

1. 把本文档提交到 `docs/tasks/` 或 `docs/architecture/`。
3. 更新 `product-structure.md` 或同类产品结构文档，说明岗位库、目标岗位、岗位管理的区别。
4. 更新前端导航和页面标题，避免普通用户看到“岗位管理”。
5. 执行一次主流程手动验收：简历 → 目标岗位 JD → 解析 → 匹配 → 建议 → 改写 → 历史。
6. 将大规模 UI 重构、后端模块重构、部署优化放入第四阶段或第五阶段，不在本次边界收敛中强行完成。

## 13. 最终目标

本次优化的目标不是把项目做得复杂，而是让项目在面试展示时更清楚：

- 用户为什么先上传简历。
- 为什么需要目标岗位。
- 为什么目标岗位以“用户粘贴真实 JD”为主，而不是爬取岗位。
- 匹配分析回答什么问题。
- 优化建议和局部改写有什么区别。
- 岗位优化报告为什么只是聚合展示。
- AI 历史为什么只负责回看。
- 后端如何体现清晰分层和业务建模能力。

最终项目应该能被一句话解释清楚：

> 这是一个基于 Java 后端和 AI 能力的简历诊断与岗位匹配分析系统，围绕“简历资产”和“用户粘贴的目标岗位 JD”构建主流程，通过解析、匹配、建议、改写和历史回看，帮助用户有依据地优化简历。
