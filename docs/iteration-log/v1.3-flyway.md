# v1.3 Flyway 数据库迁移管理

## 1. 本轮目标
引入 Flyway 数据库迁移管理，将 Phase 1 零散手动 SQL 整理为可重复执行、可追踪的迁移脚本，并让新数据库可以自动创建 MVP 所需表和预置岗位数据。

本轮不做日志规范、接口文档、CI 或复杂部署编排。

## 2. 本轮完成内容
- 添加 `flyway-core` 依赖
- 添加 `flyway-database-postgresql` 依赖
- 配置 Flyway 迁移路径为 `classpath:db/migration`
- 启用 `baseline-on-migrate`
- 将 baseline version 设置为 `0`
- 创建 `backend/src/main/resources/db/migration/`
- 创建 `V1__create_users_table.sql`
- 创建 `V2__create_resumes_table.sql`
- 创建 `V3__create_resume_parse_results_table.sql`
- 创建 `V4__create_resume_ai_analyses_table.sql`

- 为 `resumes` 表补充 `storage_type` 字段，默认值为 `LOCAL`
- 为 `resumes.storage_type` 增加 `LOCAL` / `MINIO` 检查约束

## 3. 迁移脚本
当前迁移脚本如下：

| 版本 | 文件 | 作用 |
|---|---|---|
| V1 | `V1__create_users_table.sql` | 创建用户表 |
| V2 | `V2__create_resumes_table.sql` | 创建简历表，并补充 `storage_type` |
| V3 | `V3__create_resume_parse_results_table.sql` | 创建简历解析结果表 |
| V4 | `V4__create_resume_ai_analyses_table.sql` | 创建 AI 分析结果表 |
| V5 | `V5__create_jobs_table.sql` | 创建岗位表 |
| V6 | `V6__create_job_match_results_table.sql` | 创建岗位匹配结果表 |
| V7 | `V7__seed_phase1_jobs.sql` | 写入或更新 Phase 1 预置岗位数据 |

## 4. Baseline 策略
- 新数据库：Flyway 会从 V1 开始自动创建表结构和预置岗位数据。
- 已有本地数据库：启用 `baseline-on-migrate`，并设置 baseline version 为 `0`，让现有库可以被 Flyway 接管后继续执行 V1-V7。
- 迁移脚本使用 `CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS`、`ALTER TABLE ... ADD COLUMN IF NOT EXISTS` 和 `ON CONFLICT`，降低接管已有本地库时的重复执行风险。

## 5. 关键技术点
- 使用 Flyway 统一管理数据库结构，不再推荐手动逐个执行 `db/init` 脚本。
- `db/init` 暂时保留为历史脚本，后续可在 Phase 2 收口时决定是否归档或删除。
- 预置岗位数据从建表脚本中拆出，放入独立 V7 seed 脚本，便于后续单独维护。
- `storage_type` 明确当前简历文件存储来源，为后续切换 MinIO 预留字段。

## 6. 验证记录
- 已运行后端 `./mvnw test`。

- Flyway 已对已有本地库创建 `flyway_schema_history`。
- Flyway 已成功 baseline 到 version 0。
- Flyway 已成功执行 V1 到 V7 迁移。
- 迁移过程中已有表和索引通过 `IF NOT EXISTS` 跳过，未阻塞启动。

## 7. 当前不足
- 迁移脚本目前只覆盖 Phase 1 表结构和预置岗位数据，没有设计回滚脚本。
- 已有本地库接入 Flyway 后会生成 `flyway_schema_history`，后续不应再手动改已执行的迁移脚本。
- 后续如需修改表结构，应继续新增 V8、V9 等迁移，不直接修改已经执行过的 V1-V7。
- API 集成测试的独立测试数据库初始化方式后续在 v1.6 继续完善。
