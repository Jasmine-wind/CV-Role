## 3. 关键技术点
- 历史记录不新增独立流水表，使用已有业务表做聚合查询
- 以当前登录用户 ID 作为历史记录查询边界，不接收前端传入的用户 ID
- 通过简历 ID 串联解析结果、AI 分析结果和岗位匹配结果
- 历史记录详情返回最近一次匹配和当前简历的匹配结果列表
- 后端保持 Controller、Service、VO 分层，业务代码放在 `module/history`
- 前端使用独立 `history` API 和类型定义，页面路由归入受保护页面
- Axios 响应拦截器统一处理常见网络和鉴权错误
- 后端全局异常处理补充日志，演示出错时更容易定位
- README 和阶段文档按当前真实运行方式整理，避免把 MinIO 写成 Phase 1 必需组件

## 4. 遇到的问题
- 历史记录需求容易扩展成复杂行为流水和统计功能。
- 历史记录需要同时展示简历、解析、AI 分析和岗位匹配状态，数据来自多张表。
- AI 分析摘要曾直接展示 JSON 数组字符串，不适合前端阅读。
- `/api/history/**` 初始需要确认是否纳入鉴权保护。
- Token 失效、后端未启动和请求超时时，前端提示不够统一。

## 5. 解决方式
- 历史记录采用聚合查询方式，不新增 `history_records` 表。
- 以 `resumes` 为主表，在 Service 层查询并组装解析结果、AI 分析结果和岗位匹配结果。
- 将 AI 分析摘要中的 JSON 字符串数组转换为可读文本后返回前端。
- 将 `/api/history/**` 加入 Spring Security 的 authenticated 配置。
- 前端请求层统一处理 401、超时、网络不可达和 5xx 错误。
- Token 失效时清理本地 Token，并带 `redirect` 参数跳转登录页。
- 后端全局异常处理对业务异常和未处理异常分别记录日志。

## 6. 当前不足
- 历史记录聚合当前采用 Service 层组装，适合 Phase 1 数据量；后续数据量增大时可优化为批量查询或专用 SQL。
- 简历结构化解析仍是规则基础版，复杂模板、扫描件和 OCR 不在 Phase 1 范围内。
- AI 分析依赖外部 OpenAI-compatible 服务，真实效果受模型、网络和 API Key 配置影响。
- 岗位匹配仍是基础关键词匹配，不包含向量语义匹配、RAG 或复杂权重模型。
- 当前没有正式管理后台，岗位数据主要依赖初始化 SQL。
