## 4. 遇到的问题
- 岗位数据在 Phase 1 不做完整后台，需要先通过初始化脚本保证可用。
- 岗位技能字段需要既便于 SQL 初始化，又便于后端转换为列表展示。
- 第一版匹配算法需要保持可解释，不能引入 v0.5 范围外的向量语义匹配。
- 简历结构化解析结果可能缺少技能字段，需要返回明确的低分和提示。
- 同一份简历重复匹配同一岗位时，需要避免产生多条重复结果。
- 匹配结果中的命中项、缺失项和建议需要落库，但前端不能直接依赖数据库 JSON 字符串。
- 前端需要同时处理岗位加载、简历加载、匹配触发和历史匹配结果查询，状态容易互相覆盖。
- 删除简历时如果只清理解析结果和 AI 分析，会因为 `job_match_results` 外键关联导致删除失败或残留数据。
- 真实 AI 分析在使用 `deepseek-v4-pro` 时响应较慢，影响 v0.5 联调过程中的完整演示。

## 5. 解决方式
- 使用 `v0.5.1-jobs.sql` 创建岗位表并预置 5 条岗位数据。
- 将 `required_skills` 作为 JSON 字符串保存，后端统一转换为 `List<String>`。
- 匹配算法采用岗位要求技能为基准，按命中数量计算 0 到 100 的匹配分数。
- 对技能关键词做小写、去空格和简单别名归一化处理。
- 岗位技能为空时抛出明确业务异常，简历技能为空时返回 0 分并说明信息不足。
- 使用 `(resume_id, job_id)` 唯一约束和服务层覆盖更新策略处理重复匹配。
- 使用 Jackson 将匹配结果和优化建议序列化保存，查询时再转换为前端结构化字段。
- 在匹配服务中统一校验简历归属、解析状态、岗位存在和岗位可用。
- 前端岗位详情页按加载岗位、加载简历、加载当前简历匹配结果的顺序组织状态。
- 前端对无简历、未解析、匹配失败和加载中状态分别展示提示。
- 在 `ResumeServiceImpl` 中删除简历时先清理岗位匹配结果，再清理 AI 分析、解析结果、简历记录和文件。
- 将 AI 模型名称改为 `OPENAI_MODEL` 环境变量覆盖，默认使用响应更快的 `deepseek-v4-flash`。

## 6. 当前不足
- 当前匹配算法仍是基础关键词匹配，不识别复杂语义等价关系。
- 当前岗位数据由初始化脚本预置，不提供岗位管理后台。
- 当前优化建议为规则生成，不调用 AI 生成更细粒度的岗位定制建议。
- 当前不做岗位推荐排序，只支持用户选择单个岗位进行匹配。
