# v3.3 文件存储抽象与存储策略演进

## 目标

完善文件存储抽象，使简历文件访问不依赖具体本地路径，便于后续从本地存储切换到 MinIO 或其他对象存储。

## 完成内容

| 小任务 | 状态 | 说明 |
|---|---|---|
| v3.3.1 当前文件存储实现审查 | 已完成 | 已扫描上传、读取、解析、删除、配置、数据库字段和 MinIO 预留状态 |
| v3.3.2 FileStorageService 接口规范 | 已完成 | 已将存储接口改为 `StoreFileCommand` 输入、`storageKey` 语义、文件流读取、存在性判断、元信息读取和删除能力 |
| v3.3.3 本地文件存储实现整理 | 已完成 | 已拆出本地路径解析和安全文件名组件，业务层不再直接拼接本地路径 |
| v3.3.4 MinIO 预留配置与实现方案 | 已完成 | 已补充存储类型配置和 MinIO 属性占位，当前不引入 SDK、不启用 MinIO |
| v3.3.5 文件访问安全校验 | 已完成 | 已移除上传响应中的内部 `objectKey`，补充归属拒绝测试和文件类型一致性校验 |

## 验证结果

- 已确认 Controller 不直接操作文件系统。
- 已确认简历解析通过 `FileStorageService.loadAsStream(storageKey)` 读取文件流。
- 已确认 `ResumeServiceImpl` 通过 `StoreFileCommand` 调用存储层，业务层不再传入本地目录字符串。
- 已保留数据库 `object_key` 字段兼容历史数据，后端内部语义收敛为 `storageKey`。
- 已移除 `ResumeUploadVO` 中的 `objectKey` 字段，前端上传结果不再接收内部存储引用。
- 已确认本地存储使用 `LocalStoragePathResolver` 防止路径穿越，使用 `SafeFilenameGenerator` 生成安全文件名。
- 已确认默认存储方式为本地存储，`APP_STORAGE_TYPE` 未配置时按 `local` 处理。
- 已确认 `APP_STORAGE_LOCAL_BASE_DIR` 可配置本地存储根目录，并兼容旧的 `LOCAL_STORAGE_BASE_DIR`。
- 已预留 `MINIO_ENDPOINT`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY`、`MINIO_BUCKET`、`MINIO_PUBLIC_ENDPOINT` 等 MinIO 配置。
- 已确认 MinIO 当前仅为配置和方案预留，不代表对象存储已可用。
- 已补充 PDF / DOC / DOCX 扩展名与 content-type 一致性校验。
- 已补充未归属简历删除测试，确认不会调用 `fileStorageService.delete`。
- 已补充未归属简历解析测试，确认不会调用文本提取读取文件。
- 已修复删除链路遗漏的 `ai_rewrite_suggestions` 和 `ai_resume_suggestions` 清理问题，避免生成过 AI 建议的简历因外键引用删除失败。
- 已更新 `docs/phase-4-architecture.md` 和 `docs/tasks/phase-4-task-list.md`。
- 用户手动验收已通过：上传、解析、删除和删除失败简历重试均正常。

## 当前不足

- 当前没有正式 MinIO SDK 和 `MinioFileStorageService` 实现。
- `APP_STORAGE_TYPE=minio` 当前只用于暴露缺少对象存储实现的问题，不代表当前版本可以切换到 MinIO。
- MinIO bucket 初始化、对象 metadata、异常映射和集成测试需要在后续明确接入时单独完成。
- 删除流程仍是数据库记录先删、物理文件后删；物理文件删除失败后的补偿清理留到后续一致性任务。
- `objectKey` 仍作为数据库字段和后端内部字段保留，这是兼容历史数据所需，不对前端暴露。
- 当前没有文件下载接口；如果后续新增下载接口，必须通过 `resumeId` 做用户归属校验，不能接收前端传入的 `storageKey`。

## 结果

v3.3 已完成文件存储抽象与存储策略演进。当前默认本地存储可用，业务层不再直接依赖本地路径，前端不暴露内部存储引用，MinIO 后续切换方式已明确，可以进入 v3.4 长耗时任务异步化设计。
