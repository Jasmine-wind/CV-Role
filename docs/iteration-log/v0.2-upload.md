## 1. 本轮目标
按小闭环逐步推进简历上传能力，完成前后端简历上传主链路：简历元数据表、文件存储服务、上传接口、简历列表和详情接口、前端上传页面和基础联调。

本轮只负责文件上传、文件存储和元数据管理，不进入文本提取、结构化解析、AI 分析、岗位匹配和优化建议。

## 4. 遇到的问题
- 前端访问后端上传接口时出现 CORS 拦截。
- PDF 可以上传，但 DOC 和 DOCX 因 Content-Type 差异被错误拒绝。
- DOCX 在部分场景下被 Spring multipart 默认大小限制提前拦截，前端只看到服务器内部错误。
- Postman 测试 `.txt` 时，如果 form-data 字段名没有写成 `file`，后端无法收到文件字段。
- 前端文件选择器设置 `accept=".pdf,.doc,.docx"` 后，默认只能看到支持的文件类型。
- 测试过程中误以为换用户上传后数据库没有更新，后续确认是查询条件或观察方式问题。
- 删除测试数据后自增 ID 不连续，容易误以为会影响功能。

## 5. 解决方式
- 在 `SecurityConfig` 中补充本地 Vite 常见端口，并允许上传预检请求所需请求头。
- 对 DOC 和 DOCX 放宽 Content-Type 校验，Phase 1 先基于后缀和大小保证上传闭环，内容级校验留到文本提取阶段处理。
- PDF 仍保留 `application/pdf` Content-Type 校验。
- 在 `application.yaml` 中配置 `spring.servlet.multipart.max-file-size: 10MB` 和 `spring.servlet.multipart.max-request-size: 12MB`。
- 在 `GlobalExceptionHandler` 中增加文件过大和 multipart 参数异常处理，避免统一落到“服务器内部错误”。
- 明确 Postman 上传接口必须使用 `form-data`，字段名必须为 `file`，字段类型必须为 `File`。
- 说明前端 `accept` 只是体验限制，后端仍保留真实文件类型校验。
- 使用关联查询确认 `resumes.user_id` 与实际上传用户一致。
- 明确数据库自增 ID 不要求连续，测试数据删除后的断号不影响功能。

- Phase 1 当前允许重复上传，没有做文件内容去重。
- DOC 和 DOCX 当前主要基于后缀和大小校验，内容级校验留到 v0.3 文本提取阶段。
- 还没有自动化集成测试覆盖上传、列表、详情和用户隔离。
- 前端首页还没有正式入口按钮跳转到 `/resumes`，当前主要通过直接访问路由测试。
- 简历文本提取和结构化解析尚未实现，已进入 v0.3 准备阶段。
